# Story 1.3: 迁移基座与幂等表

**Epic 1：账号与最小聊天纵切（可信基座）（本 Story：Phase 2）** · 规模 M（S=半天–1天，M=1–3天，L=3–7天；按单个开发 Agent 的上下文可完成估算）

As a 平台所有者,
I want 带版本的前向迁移与幂等键表,
So that 数据库变更可追踪、可回滚且重复请求不产生副作用.

## 验收标准（Acceptance Criteria）
**Given** 空的 MySQL 8.0 库
**When** 运行迁移
**Then** 创建 schema_migration 与 idempotency_key，所有表为 InnoDB + utf8mb4_0900_ai_ci，TEXT/BLOB/JSON 列无 DEFAULT（静态检查与 information_schema 双重验证）

**Given** 请求带 Idempotency-Key
**When** 同一请求在 24 小时内重复提交
**Then** 返回首次响应并标记 Idempotent-Replayed，不重复执行；同一键但请求内容不同返回 422，首次仍在处理中返回 409，5xx 不缓存

**Given** 迁移执行中途失败
**When** 再次运行或回滚
**Then** 失败的版本不写入 schema_migration，状态被标记为 dirty 并拒绝继续（MySQL DDL 会隐式提交，无法依赖事务回滚）；对应 down 脚本可恢复到上一版本

**Given** 并发运行迁移
**When** 两个进程同时启动
**Then** 由数据库命名锁保证只有一个执行；已应用迁移被改动时校验和不符并拒绝运行

**Given** 迁移执行中途失败
**When** 回滚
**Then** 事务回滚且 schema_migration 不记录该版本，可用回滚脚本恢复到上一版本

## 测试（含安全负面测试）
- 集成：真实 MySQL 8.0 上跑迁移、回滚、dirty 恢复与并发运行
- 安全负面：被篡改的已应用迁移（校验和）被拒；同键不同请求体不会重放他人响应；幂等键按租户与路径隔离
- 静态：迁移文件必须成对（up/down）且无 TEXT/BLOB DEFAULT；information_schema 验证字符集/引擎

## 配置与回滚
- **配置/决策点：** VG_MYSQL_DSN；幂等键 TTL 默认 24h；迁移通过 `veyrogram-api migrate up|down|status` 显式执行，服务启动不自动迁移
- **回滚方案：** 每个迁移带 down 脚本；失败后 dirty 标记阻止继续，按 down 脚本或从备份恢复；破坏性变更走 expand → migrate → contract
