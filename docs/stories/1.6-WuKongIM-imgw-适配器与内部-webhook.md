# Story 1.6: WuKongIM imgw 适配器与内部 webhook

**Epic 1：账号与最小聊天纵切（可信基座）（本 Story：Phase 2）** · 规模 M（S=半天–1天，M=1–3天，L=3–7天；按单个开发 Agent 的上下文可完成估算）

As a 平台所有者,
I want 业务服务通过 imgw 适配器调用 WuKongIM 并接收内部 webhook,
So that 所有对 IM 内核的访问有唯一受控入口.

## 验收标准（Acceptance Criteria）
**Given** IM 回调业务服务
**When** 请求来自非白名单来源或缺少路径密钥
**Then** 返回 403 并告警

**Given** imgw 适配器
**When** 调用 IM API
**Then** 只经回环/私网，调用失败重试并上报指标

**Given** 固定的 WuKongIM SHA
**When** 运行契约测试
**Then** 接口契约通过

## 测试（含安全负面测试）
- 契约：imgw 对固定 WuKongIM SHA 的接口契约测试
- 集成：IM 重启后适配器重连

## Dev Agent Record
- 状态：review。已完成：`internal/platform/imgw`（IM API 客户端：仅回环/私网、5xx/传输错误重试、4xx 不重试、观察者上报指标、`Send` 强制 client_msg_no）；`internal/platform/imwebhook`（内部回调监听器：路径密钥常量时间比较、来源白名单默认仅回环、仅 POST+JSON、64KiB 上限、失败一律 403/4xx 并计数告警、`msg.before_send` 无策略或策略出错时 fail-closed 拒绝）；配置 `VG_IM_API_URL`/`VG_IM_WEBHOOK_ADDR`/`VG_IM_WEBHOOK_SECRET`/`VG_IM_WEBHOOK_ALLOW`（严格环境校验私网与密钥强度；未设密钥则不启动回调监听）；指标与告警规则。
- 契约测试：`tools/build_wukongim.sh` 校验 upstream/WuKongIM 位于固定 SHA 7b810e08 后以 go1.26.10 构建；`internal/platform/testim` 拉起真实进程（回环端口、临时目录、覆盖默认密钥、关闭插件）。针对真实进程验证：token 注册、同一 client_msg_no 去重（含 IM 重启后仍去重）、原生 send_ban、before_send 回调线格式与业务拒绝码原样回传、回调 403 时 IM 拒发（on_error=deny）、IM 重启后适配器无需重建即恢复。
- 由真实进程发现并已纳入实现的上游事实：被禁言发送者收到 HTTP 200 + reason 25（所以适配器把 reason≠1 视为失败）；个人频道回调里的 channel_id 为复合形式（如 `bob@alice`），后续策略代码不得假设为对端裸 uid；API 发送同样会触发 before_send。
- 证据：全量 `go test -race`（含真实 MySQL 8.0.46 与真实 WuKongIM）通过；变异（路径密钥比较、来源白名单、fail-closed 默认、策略错误放行、忽略 reason）均被测试捕获。
- 未完成（诚实说明）：① CI 已加入“克隆固定 SHA 的 WuKongIM 并构建后跑契约测试”的步骤，但尚未在 GitHub Actions 上运行过（本地已跑通；fork 仓库由 1.8 建立）；② 回调 HMAC 签名依赖 fork 补丁（1.8）；③ 回调幂等去重待有消费者（msg.notify 等）时实现，目前仅 before_send 同步门且无副作用；④ before_send 回调这一跳的延迟已实测（本机回环、200 次发送：无回调 p95≈12.3ms，有回调 p95≈12.2ms，差值在噪声内）；但只含内存策略，Redis 策略与并发压测不在内；⑤ IM 各监听口（API/Manager/集群/网关）仅绑回环、debug 面关闭的负面测试已补（对本机非回环地址探测，变异验证有效）；对生产配置模板与 Nginx 的同类测试属 1.7。
