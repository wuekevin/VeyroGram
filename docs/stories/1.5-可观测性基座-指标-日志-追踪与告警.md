# Story 1.5: 可观测性基座（指标、日志、追踪与告警）

**Epic 1：账号与最小聊天纵切（可信基座）（本 Story：Phase 2）** · 规模 M（S=半天–1天，M=1–3天，L=3–7天；按单个开发 Agent 的上下文可完成估算）

As a 平台所有者,
I want 统一的指标、结构化日志、追踪与告警基座,
So that 每个后续 Story 的监控要求（DoD #7）与 Phase 2 Exit“基本监控贯通”有可落地的载体.

## 验收标准（Acceptance Criteria）
**Given** 服务运行
**When** 暴露指标
**Then** Prometheus 兼容端点仅内网可达并包含投递延迟、连接数、ACK 率、DB 连接池、推送/文件/风控/开放 API 错误率的占位指标

**Given** 日志
**When** 输出
**Then** 为结构化 JSON 带 trace_id，令牌、手机号、消息正文被脱敏过滤器移除

**Given** 告警规则
**When** 指标越界
**Then** 触发告警并路由到运维通道；监控端点本身需认证且不对公网开放（T-17）

## 测试（含安全负面测试）
- 安全负面：监控/调试端点公网不可达；日志脱敏扫描（注入令牌样例）
- 集成：OpenTelemetry 追踪贯通 API→worker→imgw
- 回归：关键指标在 /metrics 中存在

## Dev Agent Record
- 状态：review。已完成：Prometheus 文本格式指标（`internal/platform/metrics`，含投递延迟/连接数/ACK/DB 连接池/推送·文件·风控·开放 API 错误占位指标）；脱敏结构化 JSON 日志（`internal/platform/logx`，按键名与值模式移除令牌/手机号/消息正文/DSN）；trace_id 取自 X-Request-Id 并写入每条日志；`/metrics` 仅在内网监听口、需 Bearer 令牌（`VG_METRICS_TOKEN`，≥24 字节；未设置则 404 即禁用）；告警规则 `infrastructure/prometheus/veyrogram-alerts.yml`（测试保证规则只引用已导出指标）。
- 证据：全量 `go test -race` 通过；黑盒测试对真实二进制验证公网口不暴露 /metrics、/debug/pprof、/healthz；注入令牌/手机号/查询串后日志无泄漏；变异（关闭脱敏、关闭令牌校验、JWT 规则、公网挂 /metrics）均被测试捕获。
- 未完成（诚实说明）：① 追踪：未引入 OpenTelemetry SDK，而是以 W3C traceparent/X-Request-Id 贯通——API 入队时写入 trace_id，worker 取出放入 context，imgw 随调用发给 IM（有测试覆盖 API→outbox→worker→imgw→IM）；没有 span/导出器，也没有后端可看；② 告警规则已用 promtool 校验并有 5 组触发/不触发单测（变异验证有效），但未在运行中的 Prometheus/Alertmanager 上加载，阈值为未经流量校准的起点值；③ 告警路由到运维通道需运维侧配置；④ 业务指标目前为占位，由后续故事填值。
