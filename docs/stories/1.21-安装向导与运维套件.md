# Story 1.21: 安装向导与运维套件

**Epic 1：账号与最小聊天纵切（可信基座）（本 Story：Phase 2）** · 规模 M（S=半天–1天，M=1–3天，L=3–7天；按单个开发 Agent 的上下文可完成估算）

As a 平台所有者,
I want 环境预检、数据库迁移、首次管理员初始化与配置管理一体的安装向导,
So that 原生 systemd 部署可重复且不依赖 install.lock 作为鉴权.

## 验收标准（Acceptance Criteria）
**Given** 全新主机
**When** 运行预检
**Then** 检查 MySQL 8.0/Redis 7/Nginx/端口/权限并给出阻断项

**Given** 安装
**When** 完成
**Then** 创建独立 dev/test/staging/production 配置模板、日志轮转、滚动/灰度发布与回滚脚本

**Given** 已安装系统
**When** 删除 install.lock 后再次运行向导
**Then** 拒绝重新初始化（见 1.11）

## 测试（含安全负面测试）
- 集成：干净主机安装与回滚演练
- 安全负面：重复初始化、弱配置被拒
- 运维：日志轮转与健康探针

## Dev Agent Record
- 状态：review（服务端与脚本；Mac 上能做的已全部做完并用真实 MySQL / Redis / Nginx / 二进制演练，主机级验证见 `docs/ops/MANUAL-CHECKLIST.md` C9）。
- 预检（AC1）：新包 `internal/platform/preflight`，检查全部是“Host 报告的事实”的纯函数，所以每条阻断规则都有不依赖真实服务的单测，真实 Host（`OSHost`）另用真实 MySQL/Redis 集成测。检查项：平台与 systemd、root、服务账号、环境文件权限（任何人可读/组或其他人可写 = 阻断）、端口占用（仅 `-fresh`）、磁盘（<2 GiB 阻断，<10 GiB 警告）、Nginx 版本（≥1.18；识别宝塔路径）、MySQL（必须 8.0，MariaDB 拒绝；严格模式；utf8mb4；binlog ROW 给 1.22 用；local_infile）、Redis（≥7；无口令可访问；`maxmemory-policy` 必须 `noeviction`——令牌黑名单在 Redis 里，被淘汰等于撤销失效；AOF）、NTP 时钟同步。staging/production 下加固类问题是阻断，development/test 只是警告，版本过低任何环境都阻断。错误信息会擦掉口令。命令：`veyrogram-api install preflight [-install] [-fresh] [-json] [-ports]`，有阻断退出码 3，并且把配置本身的违规也列为阻断。
- 向导（AC3）：`veyrogram-api install run -username U`：配置检查 → 口令策略 → 主机预检 → 是否已安装 → 迁移 → 首个管理员。弱配置、弱口令、坏用户名都在**任何写入之前**被拒（测试断言数据库里 0 张表）；成功后写一个仅供人看的 `install.lock`（`VG_INSTALL_LOCK`），再次运行或删除该文件后再运行都被拒（退出码 4），决定来自数据库 `system_state`，不是文件；半途中断后重跑可续（迁移幂等）。口令从不回显。
- 环境分层与脚本（AC2）：`infrastructure/config/{development,test,staging,production}.env.template` 四套互不共用密钥/库/Redis/端口；`scripts/install.sh` 在主机上就地生成随机密钥（`@@GEN:…@@`，不打印、不外传）、列出必须手填项（`@@FILL:…@@`），已存在的 `api.env` 永不覆盖；服务对“仍含占位符”的值直接拒绝启动（并用测试保证变量清单与代码读取的变量一致）。演练测试 `tests/ops/test_install.sh` 用**真实二进制**验证：生成的密钥都≥32 字符且互不相同、不出现在安装输出里、文件 0640、重跑不改文件、未填写时服务拒绝、填完后 production 和 staging 配置都被严格模式接受（这一条抓到了模板漏掉 `VG_TOKEN_SIGNING_KEY`）。日志：journald 限额（2G/30 天）+ logrotate 规则（含 `logrotate -d` 与强制轮转检查，Mac 无 logrotate 时跳过，CI 运行）。
- 灰度/滚动发布与回滚：`deploy.sh`/`rollback.sh` 沿用并把公共逻辑抽到 `lib.sh`（暂存、激活+自动回滚、清理），原 14 项演练不变；新增 `canary.sh start|status|check|promote|abort`：第二实例（`veyrogram-api-canary.service` + `canary.env`，监听全部独立、管理面关闭）+ Nginx 加权上游（模板新增 `include`，没有文件=没有灰度）。`check` 读灰度实例的 `vg_http_requests_total`，请求数不足或 5xx 比例超限就拒绝 promote；任何启动失败（预检、不就绪、Nginx 拒绝配置、校验和不符）都会撤销灰度并保证流量不变；promote 失败自动回滚。用真实 Nginx 加桩进程演练（32 项）：20% 实测 400 个请求恰好 80 个到灰度。
- 健康探针：`veyrogram-api probe`（api 就绪含 MySQL、worker、IM）+ `veyrogram-probe.timer`（每分钟）+ node_exporter textfile 指标；告警 `VeyroGramProbeDown`、`VeyroGramProbeStale`（探针自己停了也能发现），promtool 单测通过。
- 过程中修掉的真实问题：① 1.19 的 `DisableAdmin` 在两个 owner 同时互相禁用时偶发 MySQL 死锁（1213）而不是干净返回 ErrLastOwner——CI 上现形，统一加锁顺序后修复，回归测试重复竞争 40 轮（旧代码第 1 轮就失败）；② `go.mod` 缺 `golang.org/x/sys`（Argon2 的 AVX2 文件只在 amd64 编译，Mac 上测不出），CI 红，已修并给 `ci_local.sh` 加了“go mod tidy 无差异”和“linux/amd64 交叉编译”两道门；③ `golang.org/x/crypto` 升到 0.52.0（GitHub 报 16 个依赖告警）；④ 管理面与 worker 默认端口同为 9103，现在配置校验会拒绝它们相同；⑤ 清单里两个“C7”编号重复，管理面改为 C8。
- 未完成（诚实说明）：① 主机级行为（真实 useradd/systemd/journald/logrotate、宝塔下的 Nginx 重载）只能在干净的 Linux 主机上验证，见清单 C9；② 灰度只分流 `/v1` HTTP 请求，IM 长连接不分流，且新旧版本共用同一个 MySQL，要求迁移向前兼容（文档已写）；③ 灰度判断只看 5xx 比例与请求数，没有延迟/业务指标对比；④ 向导没有“回滚到未安装”：迁移有 down，但首个管理员刻意不可撤销（防止被滥用）；⑤ `VG_TOKEN_SIGNING_KEY` 是遗留占位变量，仍被严格模式强制要求，待令牌密钥环完全取代后清理；⑥ 环境如何划分主机（PRD OQ-7）仍待你决定，模板两种都支持。
