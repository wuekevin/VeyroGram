# Story 1.8: WuKongIM fork、补丁与升级流程

**Epic 1：账号与最小聊天纵切（可信基座）（本 Story：Phase 2）** · 规模 M（S=半天–1天，M=1–3天，L=3–7天；按单个开发 Agent 的上下文可完成估算）

As a 平台工程团队,
I want 固定 SHA 的 WuKongIM fork、补丁（webhook HMAC）与升级验证流程,
So that 内核升级可控，无签名 webhook 等已知缺口有闭环.

## 验收标准（Acceptance Criteria）
**Given** fork
**When** 建立
**Then** 保留 upstream remote、记录固定 SHA 与 go1.26.10 工具链，变更保留许可证与署名

**Given** webhook 无签名
**When** 补丁
**Then** 增加 HMAC 签名与时间戳校验并在 imgw 校验

**Given** 升级
**When** 切换 SHA
**Then** 运行 imgw 契约测试与核心 E2E 才能放行

## 测试（含安全负面测试）
- 契约：imgw 对新 SHA 的接口契约
- 安全负面：伪造/重放 webhook 被拒
- 回归：升级后核心 E2E

## Dev Agent Record
- 状态：review。采用“固定 SHA + 补丁队列”而非托管 fork：`patches/wukongim/0001-webhook-hmac-signing.patch`（上游新增 `webhook.signing_secret`，对异步 webhook 与 before_send 回调统一加 `X-WK-Timestamp` / `X-WK-Signature: v1=hmac_sha256(ts "." body)`；含配置 schema/帮助/双语文档表同步，因为上游测试强制一致）；`tools/build_wukongim.sh` 在临时 worktree 中应用补丁并以 go1.26.10 构建，补丁不适用则构建失败，上游检出始终保持在固定 SHA。流程文档：`docs/ops/wukongim-patching.md`（补丁清单、新增/升级流程、回滚）。
- imgw 侧校验：`imwebhook.Config.SigningSecret`（`VG_IM_WEBHOOK_SIGNING_SECRET`，严格环境要求 ≥32 字节、非已知默认、不得与路径密钥相同）；签名常量时间比较、时间戳窗口默认 5 分钟；拒绝原因 `bad_signature` 进入既有拒绝计数与告警。未配置密钥时行为不变。
- 测试：上游单元测试（签名/验证/重放/篡改、两个发送器、配置一致性）通过；VeyroGram 单元测试（无签名、错误密钥、篡改正文、过期时间戳、坏时间戳、缺签名全部 403）；对真实补丁二进制的契约测试：密钥一致放行，密钥不一致则策略永不被调用、IM 因 fail-closed 拒发、拒绝被记为 bad_signature；用未打补丁的二进制跑同一测试会失败（证明测试依赖补丁）。生产配置模板新增 signing_secret 且校验器强制。
- 未完成（诚实说明）：① “fork 建立并保留 upstream remote”：未创建 GitHub fork（补丁队列已足以复现构建；如需 fork 见运维清单）；② 许可证/署名合规的法务确认未做；③ “升级后核心 E2E”：核心 E2E 要等聊天纵切（后续 Story）才存在，当前只有 imgw 契约套件；④ 只验证了单节点；⑤ 补丁尚未向上游提交。
