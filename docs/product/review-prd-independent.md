# PRD 独立评审 — VeyroGram（docs/product/PRD.md + addendum.md）

- 评审日期：2026-11-19
- 评审方式：独立上下文，未参与编写；PRD 未作任何修改
- 依据：BMAD PRD 质量评审标准（prd-validation-checklist.md，七个维度）；`BMAD-MASTER.md` §0、§4、§5、§6、§8；`docs/audit/feature-matrix.csv`（260 行，付费 121 行）；`docs/audit/risk-register.md`（R-01…R-30）
- 严重度定义：critical = 违反不可变约束或 §8 阻断项，或会让下游 Epic 无法关闭/无法上线；high = 关键需求缺失或自相矛盾，下游必然返工；medium = 可验收性或追溯不足；low = 措辞、编号、术语一致性问题

## 1. 结论：有条件通过（CONDITIONAL）

PRD 的骨架是好的：用户旅程（UJ）都有具名主角，FR 带可测后果（Consequences），非目标里明确写了 §0.8 禁止宣称的各项，反向指标（SM-C1…C3）和开放问题都是真问题，R-21（WuKongIM 内部 API 无鉴权）被提升为 NFR-2 并要求负面测试，这一点处理得很到位。

但目前还不能作为 Phase 1 的“评审通过”产物交给架构和 Story 拆分。原因有三类：
1. **§8 阻断项和 §0.3 不可变约束缺了整块需求**：Electron 和移动端的安全基线、令牌生命周期、对外端口暴露、全端 UI 重设计与设计系统、无 Emoji 图标的可测门禁，PRD 里都没有对应的 FR 或 NFR。
2. **付费模块和基础功能的追溯不完整**：约 20 行矩阵需求在 FR 中找不到可测落点；addendum 中“FR-1…13、FR-61 等”这种写法无法追溯；§4 要求的十列跨端矩阵在 PRD 和 CSV 中都不存在。
3. **几处自相矛盾**：术语表对“IM 内核”的定义与 NFR-2 冲突；撤销授权到底“立即”失效还是“≤ 60 秒”失效，FR-49 与 SM-6 说法不一；“频道”一词被两种含义同时占用。

**通过条件**：关闭下文全部 critical 与 high 项（C-1…C-3、H-1…H-11），并补齐 addendum 中逐行到 FR 的映射。

### 各维度判断

| 维度 | 判断 | 一句话理由 |
|--|--|--|
| 决策就绪度 | 基本够用 | 12 个开放问题都是真决策；但 Manager/Web 无许可证、Swagger 扩展模块是否纳入这两个决策被埋起来了（H-9、M-12） |
| 实质而非装饰 | 基本够用 | UJ 都在驱动 FR；NFR-7、NFR-9 偏模板化，缺阈值 |
| 战略一致性 | 偏弱 | 有主线（安全、可审计的重建），但 MVP 等于全量 v1，范围类型不清（M-1） |
| 完成定义清晰度 | 偏弱 | 约 1/3 的 FR 后果是形容词式的（“立即”“实时”“一致”“可用”），没有界限值（见 §4） |

## 2. 问题清单（按严重度排序）

### Critical

**C-1 §8 安全阻断项大面积缺失（客户端侧与暴露面）**（PRD §8 NFR-1…12；对照 MASTER §8、§9；风险 R-05、R-08、R-22、R-23）

PRD 的 NFR 只覆盖了服务端授权、IM 内核隔离、默认凭据、TLS、供应链和部署。MASTER §8 中下列阻断项**没有任何 FR 或 NFR 承接**：
- **Web/Electron**：CSP、XSS/CSRF/SSRF 防护、关闭 `nodeIntegration`、`contextIsolation`、安全 preload、IPC allowlist、外部链接校验。FR-57 只覆盖了“签名更新”这一项。R-05（Electron 26、React 17）没有被追溯。
- **移动端**：令牌安全存储、证书校验、备份时排除敏感数据、越狱/root 风险提示、截屏隐私提示。
- **令牌生命周期**：WebSocket token 和会话过期/续期策略（MASTER §5 P0 的“会话过期策略”、§8 的“token 生命周期”）。FR-3 只规定了撤销后多久失效。
- **暴露面**：“无鉴权监控页面/管理端口”、演示账号、“对外仅暴露必要 HTTPS/WSS”、可信代理列表（这一项 FR-44 有部分覆盖）。R-08（Grafana 默认密码、MCP token）和 R-22（adminer 8306、MinIO 9001、3306 对外）都没有被追溯。
- **QA 门禁**：SAST、DAST、secret scan、fuzz/race、安全回归（NFR-5 只写了 SBOM、许可证和依赖漏洞）。
- **威胁模型**：PRD 没有要求产出 STRIDE 威胁模型，也没有要求覆盖其中列出的重点资产。
- **文件**：转码沙箱、恶意文档预览风险（FR-22、FR-23 没有涉及）。

*修复*：新增 NFR-13“客户端安全基线”（Electron 与移动端各列可测检查项）、NFR-14“令牌与会话生命周期”（签发、续期、过期、撤销的界限值）、NFR-15“暴露面”（端口白名单，并对监控/管理端口做负面测试）、NFR-16“安全测试门禁”。同时在 addendum D 中补上 R-05、R-08、R-22、R-23 的追溯。

**C-2 §0.3 要求的全端重设计与 §0.7 无 Emoji 图标没有正向需求**（PRD §4 全部、§5 非目标；对照 MASTER §0.3、§0.7、§7、§10.6）

PRD 只在非目标里写了“不换主题冒充重设计、不用 Emoji 当图标”，**没有任何 FR 交付设计系统、品牌资产、SVG 图标库、多平台 AppIcon、视觉回归和断点截图**。Web/Desktop 的三栏布局、托盘、快捷键、文件拖拽、离线恢复通知，以及 Manager 每页“真实数据动作”，同样没有 FR（FR-47 只顺带提了 Loading/Empty/Error 状态）。结果是 Phase 1 的出口条件（设计系统、Logo 多平台输出）在 PRD 中无法追溯，也无法验收。

*修复*：新增“4.x 品牌、设计系统与端体验”特性组，至少包括：
- FR：设计 tokens 与明暗主题；
- FR：原创 SVG 图标库，可测后果为“导航/Tab/侧栏资源中检测到 Emoji 码点则 CI 失败”；
- FR：多平台图标资产清单（Adaptive/AppIcon/ICO/ICNS/PWA maskable）；
- FR：Desktop 专属能力；
- FR：视觉回归，覆盖 360/390、平板、桌面断点，暗色、中英文和字体放大。

**C-3 §0.2 要求“保留上游全部基础功能并有测试证据”，但基础版 139 行缺少验收指标和逐行追溯**（PRD §7 SM-2、SM-4；addendum A“基础版 139 → FR-1…13、FR-61 等”）

SM-4 只要求付费 121 行达到 `TESTED`；SM-2 只覆盖 6 条核心端到端用例。基础版 139 行用“等”字带过，下列基础能力**在 FR 中完全没有落点**：
- @提醒与 @消息强提醒（矩阵第 34、53 行）
- 群创建、默认头像/名称、加减成员、改群名、群主退出时自动转让（第 19–22、65、71、72、84 行）
- 群公告（第 23、73 行；§4.4 描述里提到了，但没有 FR）
- 清空远程和本地聊天记录（第 80、93 行；这牵涉删除语义）
- 语音消息 60 秒上限（第 10–13 行）
- 链接识别与预览（第 3 行；服务端抓取有 SSRF 风险）
- 好友备注、群内昵称、群备注（第 74–76、97、116 行）
- 官方/机器人账号标识（第 58、107 行）
- Web/PC 在线状态（第 59 行）
- 网络/连接/同步状态显示（第 60、61 行）
- 平台短号“只允许修改一次”（第 126 行）
- 聊天背景、清空缓存（第 137、138 行）

另外，R-16 已证实上游单测不能作为回归基线，PRD 对“如何证明无回归”没有给出要求。

*修复*：新增 SM：“基础版 139 行在关闭 Phase 3 时 100% 为 `TESTED`（每行有证据路径）”；为上面列出的缺口补 FR，或明确合并到现有 FR 的后果中；addendum A 改为逐行（行号 → FR）的映射。

### High

**H-1 术语表中“IM 内核”的定义与 NFR-2 矛盾**（§3 Glossary“IM 内核……对客户端以外**不得暴露业务 API**” vs NFR-2“仅业务服务可达”）

按术语表的字面意思，客户端可以访问 IM 内核的业务 API。这恰好是 R-21 的攻击面（`/message/send`、`/user/token`）。

*修复*：改为“客户端只能经长连接协议接入；IM 内核的 HTTP 业务/管理 API 只对业务服务开放”。

**H-2 §4 要求的十列跨端矩阵缺失**（MASTER §4：Server/Android/iOS/Web/Desktop/Manager/API/DB/通知/权限/E2E，不适用的格子要有正式说明和替代交互）

PRD 中没有任何 FR 标注适用端。`feature-matrix.csv` 只有 server、android、ios、web、desktop、manager 六列，而且值全部是 `UNVERIFIED`，缺 API、DB、通知、权限、E2E 五列。

*修复*：在 addendum 中为每个付费模块 FR 给出十列适用性表（N/A 必须有理由和替代交互），或者要求先扩展 CSV 列，再以此为准。

**H-4 MASTER §4 各模块附加要求被静默省略**
- §4.4 文件：断点续传（必要时）、配额与保留策略只在描述中出现，FR-22 没有可测后果。
- §4.9 表情商店：自定义表情包**上传**、**分享**、**版权与内容处理**都没有 FR。
- §4.11 客服：**手动分配**（FR-38 只写了自动分配）、**用户标签**都缺失。UJ-6 中“访客从官网进入咨询”对应的官网咨询组件入口也没有 FR（FR-38 只写了“通讯录内专属客服入口”）。
- §4.13 音视频：呼叫超时时长、VoIP 推送/CallKit/ConnectionService 没有可测要求；FR-37 写的是“遵守各平台前后台/来电集成”，无法测试。

**H-5 开放平台（MASTER §6）的上线硬门槛未全覆盖**（§4.19 FR-48…53、FR-63）

缺失项：
- TypeScript/Go/Android/iOS **SDK**（无 FR）
- **团队与角色**（只在描述中出现）
- **沙箱/测试账号、调试日志、版本管理**（无 FR）
- H5 应用和企业内部应用两种类型（无 FR）
- Bridge 的**版本/能力探测**、**CSP**、**资源限制**、**小程序间网络与存储隔离**（§6 列为安全隔离硬门槛）
- **跨端兼容**：同一小程序在 Android、iOS、Web、Desktop 上的运行与降级（§6“完整设计桌面 Web 与移动端安全承载”，以及硬门槛中的“跨端兼容”）
- OAuth 的 `state` 防 CSRF
- 合规支付渠道落地后才开放的小程序支付能力（应写明为门控条件）
- 开发者文档站（§5 P0）

另外，MASTER §13.6 要求单独产出 `OPEN-PLATFORM-PRD.md`，当前只占 §4.19 一节，需要说明是合并还是后续拆出。

**H-6 Web/Desktop 的登录方式未定义**（FR-1 只有手机号 + 短信；FR-11 的二维码只用于加好友和入群）

上游 Web/PC 依赖扫码登录（矩阵第 59 行“web/pc 登录显示状态”）；UJ-1 中“在已登录的 Mac 桌面端确认新设备”和“已信任设备确认”在 FR-3、FR-4 中也没有对应能力（FR-3 只写了“额外验证”，矩阵原文是“验证手机号码”）。

*修复*：新增 FR“扫码登录与可信设备批准新登录”，并写明二维码时效、绑定设备和防钓鱼确认页。

**H-7 MASTER §5 P0 中管理后台与平台能力缺 FR**
- Manager 中的**用户/设备/群/消息索引与查询**、**统计与监控报表**、**通用内容审核队列**（目前只有 FR-28 的动态审核和 FR-25 的表情审核，没有消息、群、头像、昵称的审核）、媒体管理、活动管理。
- §5 P1 的优惠券、发票/税务、套餐变更、消息自动化/工作流、活动、数据统计：可以延后，但应在 §6.2 中显式列出，不能静默缺失。

**H-8 隐私阻断项中的“数据保留”没有落成需求**（MASTER §8 隐私；PRD §9 只写了反面约束）

PRD 没有定义私聊、群聊、媒体的默认保留期，也没有要求可配置保留策略、合法调取请求（lawful request）流程、管理员访问边界的技术实现。FR-5 写的是“销毁或匿名化”，与矩阵第 196 行“注销后所有信息全部销毁”存在偏差，但没有作为有意偏离写明。

*修复*：新增 FR“消息与媒体保留策略”及“合法请求处理”；在 FR-5 中注明这是与基线的有意偏差及其理由。

**H-9 Manager/Web 无许可证（R-04）的决策被弱化**（NFR-11“用户已接受风险……发布前闭环”）

MASTER §0.6 与 §10.8 规定“许可证冲突不得标记 Release Ready”。“已接受风险”与“发布前闭环”在同一句里互相冲突。既然 §0.3 本来就要求全部界面重新设计，PRD 应当做出决策：Manager 和 Web 是净室重写，还是取得作者授权？在没有决策之前，应把它列为发布阻断。

*修复*：将 OQ-10 升级为带截止阶段的决策，并加 `[NOTE FOR PM]`。

**H-10 撤销授权的生效时间自相矛盾**（FR-49“撤销后访问令牌立即失效”、UJ-5“下一次调用立即失败” vs SM-6“撤权生效时间 ≤ 60 秒”）

*修复*：统一为一个可测界限，并说明令牌是自包含 JWT 还是需要在线校验（具体机制可放入 ADR，但界限值属于 PRD）。

**H-11 性能 SLO 不满足 MASTER §10.5**（NFR-9“不预先承诺”；SM-1 没有给出负载条件）

§10.5 要求明确的验收目标 SLO：消息交付、**连接恢复**、**关键 API 延迟**、崩溃率。PRD 缺连接恢复和关键 API 延迟两项；SM-1 的“P95 ≤ 1s”没有绑定在多大连接数和什么流量模型下测得，因此无法验收。

*修复*：为 SM-1 绑定负载档位（例如 1k、10k 连接，以及群发扇出模型）；新增连接恢复 P95 和关键 API P95/P99 两项目标。所有数值保持“验收目标”的口径。

### Medium

- **M-1 MVP 实质上就是全量 v1**（§6.1）：12 个付费模块、开放平台和官网全部列为 In Scope，MVP 的类型（解决问题型、体验型、平台型还是收入型）不清楚，也无法据此排定优先级。建议把 Phase 2–3 的纵切定义为 MVP-1，Phase 4–5 定义为 GA 范围。
- **M-2 §6.1 编号列表有误**：FR-14 同时出现在“FR-1…FR-14”和“FR-14…FR-40”两处；FR-61、FR-62 既不在 In Scope 也不在 Out of Scope，而 FR-62（对象存储生命周期）是 MASTER §5 P0 的内容。
- **M-3 §0.4“跨端能力须有统一协议、状态机、优雅降级”只有 FR-8 落地**：通话（FR-35，呼叫、振铃、忙线、超时、挂断）、订单（FR-55）、小程序版本发布（FR-51）、客服会话（FR-38）都应要求产出状态机，并做跨端一致性测试。
- **M-4 §10 测试策略缺 PRD 级要求**：环境隔离（dev/integration/staging/prod，且演示环境不得暴露线上，见 MASTER §0.5）；新旧版本消息兼容与**历史数据迁移**的 golden test（§10.2）；契约测试（§10.3）；Release Ready 失败门禁（§10.8）。R-09（WuKongIM channel promise 不可回滚）应作为迁移可回滚的约束写进需求。
- **M-5 FR-36 的弱网自适应没有阈值**（丢包率、RTT 区间、音频优先的判定标准），无法验收。
- **M-6 FR-46 的“不可篡改审计”没有可测定义**：需写明验收方式，例如追加写入、哈希链校验，或证明普通管理员和 DBA 账号的删除操作可被检出。
- **M-7 FR-41 的第二条后果是架构规则（何时引入搜索引擎），不是可测行为**，应移到 ADR 或约束章节。
- **M-8 FR-60、FR-39 的租户表述不一致**：v1 只做 tenant-aware 设计，但 FR-39 的后果中写了“跨租户不泄露”，这无法在 v1 中测试。应改为“跨技能组”，或注明租户部分在 tenant-aware 设计完成后补测。
- **M-9 密钥“可轮换”弱于 MASTER §8 的“自动轮换”**（NFR-3），需写明哪些密钥必须自动轮换、轮换周期多长。

- **M-11 R-25 的后半部分没有追溯**：Manager 运行时可以通过 `window.TSDD_CONFIG` 覆盖 `APP_URL`，dev 默认指向第三方域名 `api.botgate.cn`。应在 FR-45/47 或 NFR 中要求生产构建锁定 API 源，且不允许运行时注入。
- **M-12 addendum B 中的 Swagger 扩展模块“待 PRD 评审后决定”没有对应的开放问题**：hotline（55 个操作）、organization（46）、community、web3、tgocall 是否纳入，是一个真实的范围决策（R-30），应新增 OQ-13。
- **M-13 FR-13 中“匹配使用哈希”不足以保护隐私**：手机号空间很小，哈希可以被穷举。应要求加盐或 PSI 等方案，并对批量查询限额（具体方案可放入 ADR，但威胁本身应在 PRD 中写明）。

## 5. 术语表同义词与术语漂移

- **“频道”一词两用**：术语表把“频道 (Channel)”定义为 WuKongIM 术语，与会话一一对应；FR-58 和 §6.2 又用“频道/广播”指一种产品功能。必须改名，例如产品侧称“广播频道 (Broadcast Channel)”，或把 WuKongIM 术语写作“IM Channel”。
- **管理后台的多个叫法**：术语表定义的是“管理后台 (Manager)”，正文中混用了“运营后台”（UJ-2、FR-28）、“审核后台”（FR-23）、“后台”（FR-47、FR-56）、“商业运营后台”（§1）。
- **开放平台的多个叫法**：术语表定义的是“开放平台 (Open Platform)”，正文中混用了“开发者平台”（UJ-5 进入状态）、“开发者控制台”（UJ-5 标题）、“开发者开放平台”（§1）。
- **好友与联系人**：术语表把“好友 / 联系人 (Contact)”定义为一组同义词，正文混用。建议只保留“联系人”这一个术语名，“好友关系”作为它的属性。
- **动态与朋友圈**：术语表定义的是“动态 (Moment)”，但章节标题和 UJ-4 用的是“朋友圈”。建议在术语表中注明“朋友圈 = 动态列表界面”。
- **令牌与 token**：FR-3、UJ-1 中“令牌”和“token”混用。
- **撤回提示与撤回通知**：FR-34 中两种说法都出现了。
- **未定义的术语**：“访客”（FR-38）、“平台短号/短号”（FR-13、FR-29）、“设备锁”、“自定义表情”与“平台表情包”的区别、“工单”与举报工单（UJ-2）之间的关系，都没有进入术语表。
