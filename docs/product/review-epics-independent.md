### 2.2 阶段顺序违规（对照 BMAD-MASTER §11 与 PRD §6.1）
1. **付费模块被提前到 Phase 3**：§11 Phase 4 明确列出“标签/群管理/安全”，PRD §6.1 也把 FR-14…19 列在 Phase 4。EPICS 却把 3.5（FR-14）、4.3–4.7（FR-15…19）、5.3 设备锁、5.4 密码重设、5.6 注销（三者都是“安全与隐私模块”的付费行 193–195）、8.3（FR-23）放进了 Phase 3。PRD 说“FR 范围互不重叠”，这里与 EPICS 冲突，Phase 4 的“逐条明细交叉端验收”Exit 也因此失去对象。需要二选一：出一份 ADR 修订 PRD §6.1 和 §11 的映射，或者把这些 Story 移回 Phase 4。
2. **基础功能被推迟到 Phase 4**：在线状态（38/39/46/105）、按日期/成员/类型查找（81/82/86）、基础截屏/撤回通知（90/91）、基础收藏（29）都映射到 Epic 10/13。Phase 3 Exit（基础功能端到端）无法闭合。

4. FR-57 在 9.4（Phase 3）、19.2（Phase 6）、20.6（Phase 7）三处重复交付“强制更新/灰度”。9.4 的 AC“强制更新提供过渡窗口”和 19.2 的 AC 完全相同，职责边界不清。

## (3) 范围与大小

### 3.1 过大的 Story
113 个 Story 中 L 有 43 个（38%），M 58 个，S 12 个。规模定义写的是“单个开发 Agent 3–7 天”，但几乎每个用户向 Story 都同时要求 Server + Android + iOS + Web + Desktop 五端实现，单个 Agent 的上下文明显装不下。以下 Story 应按“服务端/契约”和“各端客户端”拆分，或按子能力拆分：
- **9.6 后台全新界面**：跨端任务写的是“全部后台页面与组件”，等于整个 Manager 重写，至少要拆成框架与布局、各业务域页面若干个。
- **7.4 推送通道**：APNs、FCM、华为、小米、OPPO、vivo（还有荣耀/魅族等）共 6 个以上通道，加上服务端 outbox、失败率监控，塞在一个 Story 里。应按通道拆，并单列 VoIP/来电推送。
- **6.4 桌面端壳**：Electron 26→受支持版本、React 17 升级、三栏布局、托盘、拖拽、签名更新，至少 3 个 Story。
- **16.8 SDK 与控制台**：4 种 SDK 加完整开发者控制台，应拆成 SDK 生成流水线、每种 SDK、控制台。
- **17.2 小程序容器**：四端容器加 Bridge 协议加包签名校验，应按端拆。
- **19.1 官网**：整站（价值页、下载、功能、FAQ、状态/帮助、法务、i18n、SEO）。
- **14.1/14.2/14.3 客服**：每个都是 L，14.3 把 SLA、知识库、质检、绩效四个子系统合在一个 Story。
- **1.1、1.5、1.6、1.7、5.5、5.6、7.1、9.2、12.1、13.1、15.1–15.3、16.3、16.4、18.1、18.2**：都是多端加复杂状态机，建议拆成服务端 Story 加客户端 Story。

## (5) 约束违规（对照 BMAD-MASTER §0、§4）

先说已核实的部分：在全部 113 个 Story 和 EPICS.md 里检索 docker/compose/E2EE/端到端加密/绝对安全/无限/反编译，以及 Emoji 字符，**没有发现直接违规**。19.1 明确禁止未经验证的宣传说法；14.1 声明 hotline Swagger 只作契约参考；15.0 要求 SFU 用原生 systemd 部署。

需要指出的隐性违规或风险：
1. **§0.3 不得沿用上游 UI**：除了 9.6 配置节的一句“不沿用上游外观”，没有任何 AC 把“各端不保留上游页面样式”变成可验收项（FR-68 的后果也没有落地）。Phase 2 的 1.4/1.5/1.6 在 6.1 和设计门禁之前就要求四端 UI，最可能的实现方式就是改上游页面。建议：Phase 2 的客户端 UI 标注为“测试夹具，不进入发布”；6.x/7.1 补 AC“与上游截图比对，结构相似度低于阈值，并经设计评审签字”。
2. **§0.4 服务端鉴权**：13.4 的 EXIF 剥离、7.2 的本地搜索过滤、13.6 的截屏事件都依赖客户端执行，没有服务端兜底或风险声明（见 §4）。
3. **§0.7 Emoji 门禁**：`tools/lint_no_emoji_nav.py` 自述是“启发式，不能证明不存在”，按路径或行关键词匹配。Android 的 menu XML、BottomNavigation 和 iOS 的 TabBarItem 有可能漏检。6.2 的 AC 应补各端的正反样例（尤其 Android `menu/*.xml`、iOS storyboard/SwiftUI `tabItem`）。
4. **§0.5 部署**：没有违规。Redis 7.x 与 BMAD“Redis 8”不一致，但 ARCHITECTURE/NFR-4 已记录为用户决策，可以接受。CI 中使用 service container 不属于“正式部署”，可以接受，但建议在 1.9 写明。
5. **§0.8 宣传口径**：“≤60s 撤销”“≤5s 撤回扩散”等都标了 [假设/待测]，合规。不过 1.5 的 AC 与架构矛盾（§4），按现方案交付会在验收时形成“已达标”的错误声明。
6. **§0.6 许可**：没有发现复制闭源代码。11.5 要求登记表情素材版权，13.4 要求滤镜资源原创或 OFL，合规。
7. **§4 付费模块完整性**：12 个模块都有 Story，**没有整块缺失**。以下细项缺失：客服“手动分配/改派”；表情“用户上传自定义表情包（整包）”只做了单个表情；群管理“群头像”（行 184）、“群主退出自动转让”（行 83）；截屏“拦截”（行 143）；音视频“系统电话集成”被后置到 15.4 且依赖 OQ-5；文件“配额策略”只在配置节；收藏“权限与同步”只在测试节。§4 还要求“十列矩阵中未适用的列要有正式说明和替代交互”，现在多数 N/A 只写了“不涉及”，缺替代交互说明（如 10.2 Web 发送位置、14.2 用户侧）。
